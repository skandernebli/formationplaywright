Module 4.1 — Git avancé pour un projet de tests

Travailler en équipe sur un framework de tests : branches, conventions, revue de code.

Objectif

Adopter un workflow Git professionnel adapté à un projet de tests automatisés : stratégie de branches, conventions de commit lisibles, et savoir relire une Pull Request de tests avec un œil critique.

Explication

Stratégie de branches. Le modèle le plus courant en entreprise reste simple : une branche principale toujours stable (main), et une branche courte par fonctionnalité ou correctif (feature/tests-panier, fix/flaky-login), fusionnée via Pull Request après revue. Pour un framework de tests, chaque nouvelle suite de tests ou refactorisation d'architecture mérite sa propre branche, même sur un projet solo — cela isole le travail en cours et facilite la revue.

Conventions de commit. Un message de commit devrait décrire l'intention, pas juste l'action : "Ajoute les tests du parcours de paiement" plutôt que "update". La convention Conventional Commits (feat:, fix:, refactor:, test:) est largement répandue et facilite la lecture de l'historique, voire l'automatisation de changelogs.

Revue de code sur des tests. Relire une Pull Request de tests demande une grille de lecture spécifique : le test est-il indépendant des autres ? Utilise-t-il le Page Object Model correctement ? Les assertions sont-elles pertinentes et suffisantes (pas juste "le bouton existe") ? Y a-t-il des waitForTimeout ou des locators fragiles introduits ? Ce réflexe de relecture est une compétence à part entière, distincte de l'écriture de tests.

Démonstration

# Créer une branche dédiée pour une nouvelle suite de tests
git checkout -b feature/tests-paiement

# Commits avec convention Conventional Commits
git add tests/paiement.spec.ts pages/PaiementPage.ts
git commit -m "feat: ajoute les tests du parcours de paiement par carte"

git add tests/paiement.spec.ts
git commit -m "fix: corrige un locator ambigu sur le bouton de validation"

# Pousser la branche et ouvrir une Pull Request depuis GitHub
git push -u origin feature/tests-paiement
# Grille de relecture d'une PR de tests (à garder sous la main)
# - Le test est-il indépendant (pas de dépendance à l'ordre d'exécution) ?
# - Les locators sont-ils robustes (getByRole/getByLabel en priorité) ?
# - Les assertions couvrent-elles réellement le comportement attendu ?
# - Le Page Object Model est-il respecté (pas de locator brut dans le test) ?
# - Y a-t-il un waitForTimeout ou une attente arbitraire à justifier/supprimer ?
# - Les données/secrets sont-ils correctement externalisés ?

Mise en pratique

  1. Crée une branche dédiée pour une nouvelle suite de tests sur ton projet fil rouge, avec des commits suivant la convention Conventional Commits.
  2. Ouvre une Pull Request (même sans relecteur, le fait de la formaliser via GitHub compte) et rédige sa description en expliquant ce qu'elle apporte.
  3. Applique la grille de relecture ci-dessus à ta propre PR, en tant qu'auto-relecture critique avant fusion — c'est un excellent entraînement.

Approfondissement

  • Piège fréquent : des branches qui vivent trop longtemps sans être fusionnées, accumulant des conflits avec main — préférer des branches courtes et des PR de taille raisonnable, plus faciles à relire correctement.
  • Un message de commit qui explique le pourquoi plutôt que le quoi évident (le diff montre déjà quoi a changé) apporte une vraie valeur à l'historique, notamment pour un correctif de flaky test dont la cause n'est pas évidente à la seule lecture du code.
  • En entreprise, la relecture de PR de tests est souvent négligée par rapport au code applicatif — un SDET qui applique une grille de relecture rigoureuse à ses propres tests et à ceux de l'équipe apporte une vraie valeur différenciante.

Validation

  1. Pourquoi préfère-t-on des branches courtes plutôt que des branches qui vivent plusieurs semaines ?
  2. Cite trois points spécifiques à vérifier lors de la relecture d'une Pull Request de tests.
  3. Quel est l'intérêt d'un message de commit qui explique le "pourquoi" plutôt que le "quoi" ?

Synthèse

  • Branches courtes par fonctionnalité, fusionnées via Pull Request après revue.
  • Conventional Commits pour un historique lisible et exploitable.
  • La relecture de tests suit une grille spécifique (indépendance, robustesse, pertinence des assertions).

Module 4.2 — CI/CD avec GitHub Actions

Exécuter automatiquement la suite de tests à chaque changement de code.

Objectif

Écrire un workflow GitHub Actions qui exécute la suite de tests Playwright à chaque push et Pull Request, et configurer la récupération des rapports et traces comme artefacts consultables.

Explication

Un workflow GitHub Actions est défini dans un fichier YAML sous .github/workflows/. Il décrit un déclencheur (on: push, on: pull_request...), un environnement d'exécution (une machine virtuelle Ubuntu typiquement), et une suite d'étapes : installer les dépendances, installer les navigateurs Playwright, exécuter les tests, et publier les résultats.

Playwright fournit une image Docker officielle et une commande dédiée pour installer les navigateurs en CI (npx playwright install --with-deps), qui inclut les dépendances système nécessaires, absentes par défaut sur une machine CI vierge.

Les artefacts sont des fichiers générés pendant le workflow (rapport HTML, traces des échecs) que GitHub Actions conserve et rend téléchargeables après l'exécution — essentiel puisqu'on ne peut pas observer l'exécution en CI en direct, contrairement au local.

Démonstration

# .github/workflows/tests.yml
name: Tests Playwright

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Installer les dépendances
        run: npm ci

      - name: Installer les navigateurs Playwright
        run: npx playwright install --with-deps

      - name: Exécuter les tests
        run: npx playwright test
        env:
          BASE_URL: ${{ secrets.RECETTE_BASE_URL }}
          API_TOKEN: ${{ secrets.API_TOKEN }}

      - name: Publier le rapport comme artefact
        if: always() # même si les tests échouent, on veut le rapport
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 14

Mise en pratique

  1. Crée le fichier .github/workflows/tests.yml dans ton projet fil rouge, en l'adaptant à ta structure.
  2. Configure les secrets nécessaires (URL, tokens) dans les paramètres du dépôt GitHub, jamais en clair dans le YAML.
  3. Pousse une branche et ouvre une Pull Request pour déclencher le workflow, puis observe son exécution dans l'onglet Actions de GitHub.
  4. Volontairement, fais échouer un test et vérifie que le rapport reste bien téléchargeable en artefact malgré l'échec.

Approfondissement

  • Piège fréquent : oublier if: always() sur l'étape de publication d'artefact — par défaut, une étape ne s'exécute que si les précédentes ont réussi, ce qui prive exactement des rapports dont on a besoin quand les tests échouent.
  • Ne jamais mettre un secret en clair dans le fichier YAML, même sur un dépôt privé — toujours passer par les GitHub Secrets configurés dans les paramètres du dépôt.
  • Sur un projet volumineux, sharder l'exécution des tests sur plusieurs jobs parallèles (--shard=1/3, --shard=2/3...) réduit significativement le temps total du pipeline — une optimisation à considérer une fois la base fonctionnelle en place.

Validation

  1. À quoi sert if: always() sur l'étape de publication du rapport, et que se passerait-il sans elle ?
  2. Pourquoi les secrets ne doivent-ils jamais apparaître en clair dans un fichier de workflow ?
  3. Pourquoi npx playwright install --with-deps est-il nécessaire en CI alors qu'il n'est pas toujours utilisé en local ?

Synthèse

  • Un workflow GitHub Actions déclenche l'exécution des tests à chaque push/PR, dans un environnement isolé.
  • Les artefacts (rapport, traces) doivent être publiés même en cas d'échec (if: always()).
  • Secrets toujours via GitHub Secrets, jamais en clair dans le YAML.

Module 4.3 — Stratégie de test en contexte agile

Savoir quand automatiser, comment prioriser, et comment communiquer les résultats.

Objectif

Situer l'automatisation dans une stratégie de test globale (pyramide des tests), décider quand automatiser un scénario plutôt qu'un autre, et savoir intégrer ce travail dans le rythme d'un sprint agile.

Explication

Pyramide des tests. Le modèle classique représente trois niveaux : beaucoup de tests unitaires (rapides, ciblés, à la charge des développeurs), un nombre modéré de tests d'intégration/API (comme ceux du module 3.1, plus rapides et stables qu'un test UI), et peu de tests end-to-end UI (lents, plus fragiles, mais seuls capables de valider un vrai parcours utilisateur de bout en bout). L'erreur fréquente est d'inverser la pyramide : trop de tests UI lourds pour des vérifications qui auraient pu être couvertes plus bas, plus vite et plus stablement.

Quand automatiser. Tous les scénarios ne méritent pas d'être automatisés. Les bons candidats : parcours critiques exécutés fréquemment, scénarios de non-régression sur des fonctionnalités stables, cas répétitifs et fastidieux en test manuel. À l'inverse, un test exploratoire ponctuel, une fonctionnalité encore instable en cours de développement, ou un scénario visuel très spécifique valent parfois mieux en test manuel ou en test visuel dédié.

Intégration dans un sprint. L'automatisation d'un scénario s'intègre généralement en fin de développement d'une fonctionnalité, une fois son comportement stabilisé — automatiser trop tôt entraîne une réécriture coûteuse à chaque évolution en cours de sprint. Une pratique répandue consiste à inclure "tests automatisés écrits et passants" comme critère de "Definition of Done" d'un ticket.

Communication. Un rapport de tests n'a de valeur que s'il est lu et compris par l'équipe : un résumé clair (taux de réussite, tendance, tests instables récurrents) partagé régulièrement (stand-up, canal dédié) vaut mieux qu'un rapport détaillé jamais consulté.

Démonstration

Pyramide des tests — répartition indicative sur un projet type

        /\
       /UI\          ~10% — parcours critiques de bout en bout
      /------\
     /  API   \       ~30% — logique métier, contrats d'API
    /----------\
   /   Unitaire  \    ~60% — fonctions, composants isolés
  /----------------\

Grille de décision "automatiser ou non" :
- Exécuté à chaque sprint / release ?           → Oui : bon candidat
- Fonctionnalité stable (pas en cours de dev) ?  → Oui : bon candidat
- Coût de test manuel élevé (répétitif, long) ?  → Oui : bon candidat
- Fonctionnalité encore instable / exploratoire ? → Non : garder en manuel pour l'instant

Mise en pratique

  1. Liste 8 à 10 scénarios de test (réels ou imaginés) sur ton projet fil rouge.
  2. Pour chacun, applique la grille de décision et classe-le : à automatiser en priorité, à automatiser plus tard, à garder en test manuel.
  3. Pour les scénarios "à automatiser", identifie à quel niveau de la pyramide chacun devrait se situer (unitaire — hors de ton périmètre QA mais à signaler, API, ou UI).
  4. Rédige un résumé de 3-4 phrases, dans un format que tu partagerais réellement à une équipe, sur l'état actuel de ta suite de tests du projet fil rouge.

Approfondissement

  • Piège fréquent : une pyramide inversée où l'essentiel de la couverture repose sur des tests UI lourds — symptôme classique d'une équipe QA isolée du développement, sans tests unitaires ni API pris en charge en amont.
  • L'automatisation n'est pas un objectif en soi : un scénario testé une seule fois dans toute la vie du produit n'a probablement pas besoin d'être automatisé, le coût de maintenance dépasserait le bénéfice.
  • En entreprise, la stratégie de test se discute avec l'équipe (développeurs, product owner), pas uniquement décidée en silo par la QA — la répartition entre unitaire/API/UI dépend aussi de ce que les développeurs couvrent déjà eux-mêmes.

Validation

  1. Pourquoi une pyramide des tests "inversée" (beaucoup d'UI, peu d'API/unitaire) pose-t-elle problème ?
  2. Cite trois critères qui font d'un scénario un bon candidat à l'automatisation.
  3. Pourquoi automatiser une fonctionnalité encore en cours de développement est-il généralement une mauvaise idée ?

Synthèse

  • Pyramide des tests : beaucoup d'unitaire, un peu d'API, peu d'UI — chaque niveau a son rôle.
  • Automatiser se décide selon la fréquence d'exécution, la stabilité, et le coût du test manuel.
  • Un rapport de tests n'a de valeur que s'il est communiqué de façon claire et régulière à l'équipe.

Module 4.4 — Revue finale et documentation

Transformer le framework en un livrable professionnel, documenté et présentable.

Objectif

Documenter le framework fil rouge comme un projet d'entreprise réel : README complet, conventions de code explicites, guide de contribution — de quoi permettre à une autre personne de le reprendre sans accompagnement.

Explication

Un framework de tests non documenté perd une grande partie de sa valeur dès qu'il doit être repris par quelqu'un d'autre — ou par toi-même, six mois plus tard. Un README professionnel couvre généralement : une présentation courte du projet et de son périmètre, les prérequis et l'installation, comment exécuter les tests (localement, par tag, par navigateur), comment lire les rapports, et l'architecture générale (structure des dossiers, où trouver quoi).

Un guide de contribution (souvent CONTRIBUTING.md) formalise les conventions déjà pratiquées durant la formation : nommage des fichiers de test, structure attendue d'un Page Object, convention de commit, grille de relecture de PR — de quoi garantir une cohérence dans le temps, même à plusieurs contributeurs.

Cette revue finale est aussi l'occasion de relire l'ensemble du framework avec un regard d'ensemble : cohérence entre les modules, duplication éventuelle à factoriser, tests devenus obsolètes à retirer — un exercice de maintenance à long terme qui distingue un projet vivant d'un empilement de code qui fonctionne "pour l'instant".

Démonstration

# README.md — structure type

## Framework de tests automatisés — [Nom du projet]

### Présentation
Ce framework couvre les parcours UI et API de [application], construit avec
Playwright et TypeScript selon le Page Object Model.

### Prérequis
- Node.js 20+
- Un fichier .env configuré (voir .env.example)

### Installation
\`\`\`
npm install
npx playwright install --with-deps
\`\`\`

### Exécution des tests
\`\`\`
npx playwright test                 # suite complète
npx playwright test tests/panier    # un dossier ciblé
npx playwright test --project=chromium
\`\`\`

### Architecture
- tests/     : scénarios de test
- pages/     : Page Objects
- fixtures/  : fixtures personnalisées (auth, données)
- data/      : jeux de données et factories

### Rapports
Après exécution : npx playwright show-report

### Conventions
Voir CONTRIBUTING.md

Mise en pratique

  1. Rédige un README.md complet pour ton projet fil rouge, en suivant la structure ci-dessus et en l'adaptant à ton contenu réel.
  2. Rédige un CONTRIBUTING.md qui formalise tes propres conventions établies au fil des phases précédentes (nommage, structure des Page Objects, format de commit).
  3. Relis l'ensemble du framework avec un regard critique : repère au moins une duplication ou une incohérence à corriger, et corrige-la.
  4. Demande-toi honnêtement : une personne qui n'a jamais vu ce projet pourrait-elle l'installer et exécuter les tests en suivant uniquement le README ? Ajuste si nécessaire.

Approfondissement

  • Piège fréquent : une documentation écrite une fois puis jamais mise à jour, qui devient trompeuse plus vite qu'utile — la documentation d'un framework vivant se maintient au même rythme que le code lui-même.
  • Un README trop long décourage la lecture autant qu'un README absent : viser l'essentiel pour démarrer, avec des liens ou des sections dépliables pour les détails avancés si nécessaire.
  • En entretien ou en contexte professionnel, ce README et cette documentation sont souvent la première chose regardée avant même le code — ils reflètent directement ta capacité à produire un livrable réellement exploitable par une équipe.

Validation

  1. Quels éléments essentiels un README de framework de tests devrait-il toujours couvrir ?
  2. Pourquoi une documentation jamais mise à jour peut-elle devenir pire que l'absence de documentation ?
  3. À quoi sert concrètement un fichier CONTRIBUTING.md distinct du README ?

Synthèse

  • Un README complet couvre présentation, installation, exécution, architecture et rapports.
  • CONTRIBUTING.md formalise les conventions pour garantir la cohérence dans le temps.
  • La documentation se maintient dans la durée, au même rythme que le code.
