Module 1.1 — Locators et stratégies de sélection

La base de tout : comment Playwright trouve les éléments sur une page.

Objectif

Choisir et écrire le bon locator pour n'importe quel élément d'une page, en priorisant les locators orientés utilisateur plutôt que des sélecteurs techniques fragiles.

Explication

Playwright a une philosophie différente de Selenium sur ce point : plutôt que de cibler des éléments par leur structure HTML (CSS/XPath), il encourage à cibler ce qu'un utilisateur percevrait — un rôle, un texte visible, un label. C'est ce qu'on appelle les locators "user-facing". Ils sont plus lisibles et beaucoup plus résistants aux changements de structure du code (un développeur qui renomme une classe CSS ne casse pas le test).

Les locators principaux, par ordre de préférence : getByRole (le plus robuste — cible par rôle ARIA et nom accessible, ex. un bouton nommé "Valider"), getByLabel (pour les champs de formulaire associés à un label), getByText (pour du texte visible), getByTestId (quand aucune des options précédentes n'est fiable, on cible un attribut data-testid ajouté spécifiquement pour les tests).

Les locators sont "paresseux" (lazy) : les créer ne cherche rien dans la page tant qu'on n'exécute pas une action ou une assertion dessus. Cela permet de les chaîner et de les filtrer, par exemple pour cibler un élément précis dans une liste de résultats similaires.

Démonstration

import { test, expect } from "@playwright/test";

test("locators de base", async ({ page }) => {
  await page.goto("https://example.com/login");

  // Par rôle : le plus robuste, recommandé en priorité
  await page.getByRole("button", { name: "Se connecter" }).click();

  // Par label associé à un champ
  await page.getByLabel("Adresse email").fill("test@exemple.com");

  // Par texte visible
  await page.getByText("Mot de passe oublié ?").click();

  // Chaînage et filtrage : cibler une ligne précise dans une liste
  await page
    .getByRole("listitem")
    .filter({ hasText: "Produit A" })
    .getByRole("button", { name: "Ajouter au panier" })
    .click();

  // En dernier recours seulement : data-testid
  await page.getByTestId("cart-total").click();
});

Mise en pratique

  1. Ouvre une page web publique de ton choix (un site e-commerce par exemple) et, via les outils de développement du navigateur, identifie 5 éléments différents (un bouton, un champ de saisie, un lien, un titre, un élément dans une liste).
  2. Pour chacun, écris le locator Playwright le plus robuste possible sans utiliser getByTestId si une meilleure option existe.
  3. Si deux éléments ont le même texte visible, utilise .filter() ou .first()/.nth() pour lever l'ambiguïté et explique pourquoi ton choix est préférable à un simple .first() "au hasard".

Approfondissement

  • Piège fréquent : utiliser des sélecteurs CSS basés sur des classes générées automatiquement (ex. .css-1a2b3c) — ils changent à chaque build et rendent les tests fragiles dès le premier déploiement.
  • Si l'application ne propose aucun élément identifiable proprement, c'est un signal à remonter à l'équipe de développement : demander l'ajout d'un data-testid ou d'un attribut ARIA est une pratique QA légitime et courante.
  • Un locator qui matche plusieurs éléments ne lève pas d'erreur à sa création, mais seulement au moment de l'action — un comportement à bien comprendre pour ne pas être surpris en debug.

Validation

  1. Pourquoi getByRole est-il en général préféré à un sélecteur CSS ?
  2. Dans quel cas légitime utilise-t-on getByTestId ?
  3. Que se passe-t-il si un locator matche plusieurs éléments au moment d'un .click() ?

Synthèse

  • Priorité : getByRole > getByLabel > getByText > getByTestId en dernier recours.
  • Les locators sont paresseux et chaînables/filtrables.
  • Un bon locator résiste aux changements de structure HTML, pas seulement au contenu visible aujourd'hui.

Module 1.2 — Interactions et formulaires

Cliquer, saisir, cocher, sélectionner, uploader — automatiser un parcours utilisateur complet.

Objectif

Automatiser n'importe quel formulaire web courant : champs texte, cases à cocher, boutons radio, menus déroulants, upload de fichiers, y compris sur plusieurs étapes.

Explication

Chaque type d'élément a sa méthode dédiée : .fill() pour un champ texte (vide le champ puis tape la valeur d'un coup, contrairement à .type() qui simule une frappe touche par touche — .fill() est à privilégier sauf besoin spécifique de déclencher des événements clavier), .check()/.uncheck() pour les cases à cocher, .selectOption() pour les menus déroulants natifs (<select>), .setInputFiles() pour l'upload.

Pour un formulaire multi-étapes (wizard), le principe reste le même : on interagit avec chaque étape puis on attend que l'étape suivante soit visible avant de continuer — Playwright gère cette attente automatiquement grâce à l'auto-waiting (approfondi au module 1.3), il n'y a donc généralement pas besoin d'attente manuelle entre les étapes.

Démonstration

import { test, expect } from "@playwright/test";

test("formulaire d'inscription complet", async ({ page }) => {
  await page.goto("https://example.com/inscription");

  await page.getByLabel("Prénom").fill("Camille");
  await page.getByLabel("Nom").fill("Durand");
  await page.getByLabel("Email").fill("camille.durand@exemple.com");

  // Case à cocher
  await page.getByLabel("J'accepte les conditions générales").check();

  // Bouton radio
  await page.getByLabel("Homme").check();

  // Menu déroulant natif
  await page.getByLabel("Pays").selectOption("France");

  // Upload de fichier
  await page.getByLabel("Photo de profil").setInputFiles("fixtures/avatar.png");

  await page.getByRole("button", { name: "Créer mon compte" }).click();

  await expect(page.getByText("Bienvenue, Camille")).toBeVisible();
});

Mise en pratique

  1. Trouve (ou utilise demoqa.com/automation-practice-form) un formulaire public comportant au moins : champs texte, boutons radio, cases à cocher et un menu déroulant.
  2. Écris un test qui remplit l'intégralité du formulaire et le soumet.
  3. Ajoute une assertion qui vérifie qu'un message de confirmation apparaît après soumission.

Approfondissement

  • Piège fréquent : utiliser .type() par habitude (venant de Selenium) alors que .fill() est plus rapide et suffisant dans l'immense majorité des cas — ne réserver .pressSequentially() qu'aux cas où l'application réagit réellement à chaque frappe (ex. autocomplétion en temps réel).
  • Pour les menus déroulants personnalisés (non-natifs, construits en div/JS), .selectOption() ne fonctionne pas : il faut cliquer pour ouvrir le menu puis cliquer sur l'option comme un utilisateur le ferait.
  • Toujours vérifier le résultat d'une soumission de formulaire (message de succès, redirection, apparition d'un élément) — un formulaire qui "semble" rempli et soumis sans vérification ne prouve rien.

Validation

  1. Quelle est la différence entre .fill() et .pressSequentially(), et quand utiliser chacun ?
  2. Pourquoi .selectOption() ne fonctionne-t-il pas sur un menu déroulant personnalisé en JavaScript ?
  3. Pourquoi faut-il toujours vérifier le résultat après soumission d'un formulaire ?

Synthèse

  • Une méthode dédiée par type d'élément : .fill(), .check(), .selectOption(), .setInputFiles().
  • Les formulaires multi-étapes se traitent séquentiellement grâce à l'auto-waiting.
  • Toute soumission de formulaire se conclut par une assertion sur le résultat, jamais par la seule action.

Module 1.3 — Assertions et synchronisation

Comprendre l'auto-waiting : le mécanisme qui rend Playwright fiable par défaut.

Objectif

Utiliser correctement les assertions "web-first" de Playwright et comprendre précisément ce que l'auto-waiting fait — et ne fait pas — pour savoir quand une attente explicite reste nécessaire.

Explication

Les assertions Playwright (expect(locator).toBeVisible(), .toHaveText(), .toHaveValue(), etc.) sont dites "web-first" : elles réessaient automatiquement pendant un délai configurable (par défaut 5 secondes) jusqu'à ce que la condition soit vraie, ou échouent si le délai est dépassé. C'est fondamentalement différent d'une assertion classique qui vérifie une valeur figée à un instant T.

De la même manière, les actions (.click(), .fill()...) attendent automatiquement que l'élément soit "actionnable" : présent dans le DOM, visible, stable (pas en cours d'animation), non désactivé, et qui reçoit bien les événements (pas masqué par un autre élément). C'est ce mécanisme — l'auto-waiting — qui rend inutiles la plupart des sleep() ou wait() explicites qu'on trouve dans d'autres frameworks.

L'auto-waiting ne résout cependant pas tout : il attend qu'un élément soit prêt, mais ne "sait" pas qu'une requête réseau spécifique doit se terminer avant qu'une action ait un sens métier. Dans ces cas précis (attendre une réponse API, un événement réseau particulier), une attente explicite via page.waitForResponse() ou page.waitForLoadState() reste justifiée — mais elle doit rester l'exception, pas le réflexe.

Démonstration

import { test, expect } from "@playwright/test";

test("assertions web-first et contenu dynamique", async ({ page }) => {
  await page.goto("https://example.com/produits");

  // Assertion classique sur un état stable
  await expect(page.getByRole("heading", { name: "Nos produits" })).toBeVisible();

  // Contenu chargé de façon asynchrone (ex. via une requête API après clic)
  await page.getByRole("button", { name: "Charger plus" }).click();

  // L'assertion réessaie automatiquement jusqu'à 5s : pas besoin de sleep ici
  await expect(page.getByText("24 produits affichés")).toBeVisible();

  // Cas où une attente explicite reste justifiée : une requête réseau précise
  const responsePromise = page.waitForResponse(
    resp => resp.url().includes("/api/panier") && resp.status() === 200
  );
  await page.getByRole("button", { name: "Ajouter au panier" }).click();
  await responsePromise;

  await expect(page.getByTestId("cart-count")).toHaveText("1");
});

Mise en pratique

  1. Trouve une page avec du contenu qui se charge après un délai ou une action (spinner, chargement infini, filtre appliqué dynamiquement).
  2. Écris un test qui déclenche ce chargement puis vérifie le résultat final avec une assertion web-first, sans aucun waitForTimeout.
  3. Identifie ensuite un cas (réel ou imaginé) où une attente explicite sur une réponse réseau serait justifiée, et écris le code correspondant.

Approfondissement

  • Piège fréquent et grave : ajouter des page.waitForTimeout(3000) "au cas où" — cela ralentit inutilement les tests quand ce n'est pas nécessaire, et ne les rend pas fiables pour autant quand ce l'est vraiment (le délai fixe peut toujours être trop court sur un environnement plus lent, comme la CI).
  • Si un test échoue par intermittence malgré l'auto-waiting, la cause est souvent ailleurs : une assertion qui vérifie le mauvais élément, une action qui a un effet de bord non attendu, ou une vraie race condition réseau — creusé en profondeur en Phase 3 (flaky tests).
  • Le délai par défaut de 5 secondes se configure globalement (expect.timeout dans playwright.config.ts) ou localement par assertion — à ajuster avec parcimonie, pas comme solution de facilité.

Validation

  1. Qu'est-ce qui rend une assertion Playwright "web-first", et en quoi diffère-t-elle d'une assertion classique ?
  2. Cite trois conditions que Playwright vérifie automatiquement avant d'exécuter un .click().
  3. Pourquoi page.waitForTimeout() est-il considéré comme un anti-pattern à éviter par défaut ?

Synthèse

  • Actions et assertions réessaient automatiquement — c'est le mécanisme central de fiabilité de Playwright.
  • Les attentes explicites (waitForResponse, etc.) restent justifiées pour des conditions métier précises, jamais comme filet de sécurité générique.
  • waitForTimeout est un anti-pattern à éviter presque systématiquement.

Module 1.4 — Navigation avancée

Onglets, popups, iframes, téléchargements, dialogues natifs.

Objectif

Gérer les scénarios de navigation qui sortent d'une simple page unique : ouverture de nouveaux onglets, popups d'authentification, contenus dans des iframes, téléchargements de fichiers et boîtes de dialogue natives du navigateur.

Explication

Onglets et popups. Chaque onglet ou fenêtre est représenté par un objet page distinct dans Playwright, rattaché au même context (le "profil navigateur" de la session de test). Pour capturer une nouvelle page qui s'ouvre suite à une action (ex. un lien target="_blank"), on écoute l'événement context.waitForEvent("page") en même temps qu'on déclenche l'action.

iframes. Un iframe est une page HTML imbriquée dans une autre — fréquent pour les widgets de paiement ou les formulaires tiers. Playwright y accède via page.frameLocator(), qui fonctionne ensuite exactement comme un locator classique à l'intérieur du cadre.

Téléchargements. On capture un téléchargement de la même façon qu'un nouvel onglet : en écoutant l'événement page.waitForEvent("download") autour de l'action qui le déclenche, puis en récupérant le fichier via l'objet download retourné.

Dialogues natifs. Les alert(), confirm() et prompt() du navigateur bloquent l'exécution tant qu'ils ne sont pas traités : on écoute l'événement page.on("dialog", ...) pour les accepter ou les rejeter automatiquement.

Démonstration

import { test, expect } from "@playwright/test";

test("ouverture d'un nouvel onglet (paiement externe)", async ({ page, context }) => {
  await page.goto("https://example.com/commande");

  const [popup] = await Promise.all([
    context.waitForEvent("page"),
    page.getByRole("link", { name: "Payer via PaymentCo" }).click(),
  ]);

  await popup.waitForLoadState();
  await expect(popup.getByRole("heading", { name: "Paiement sécurisé" })).toBeVisible();
});

test("interaction avec un iframe", async ({ page }) => {
  await page.goto("https://example.com/paiement");

  const cardFrame = page.frameLocator("iframe[title='Formulaire carte bancaire']");
  await cardFrame.getByLabel("Numéro de carte").fill("4242424242424242");
});

test("gestion d'un dialogue de confirmation natif", async ({ page }) => {
  page.on("dialog", dialog => dialog.accept());

  await page.goto("https://example.com/compte");
  await page.getByRole("button", { name: "Supprimer mon compte" }).click();
  // Le dialog "Êtes-vous sûr ?" est automatiquement accepté
});

test("téléchargement d'un fichier", async ({ page }) => {
  await page.goto("https://example.com/factures");

  const [download] = await Promise.all([
    page.waitForEvent("download"),
    page.getByRole("button", { name: "Télécharger la facture" }).click(),
  ]);

  await download.saveAs("downloads/" + download.suggestedFilename());
});

Mise en pratique

Sur le projet fil rouge (e-commerce/back-office) ou un site public équivalent :

  1. Écris un scénario qui déclenche l'ouverture d'un nouvel onglet et vérifie du contenu dessus.
  2. Si le site utilise des dialogues natifs (ou simule-le avec une page de test simple contenant un bouton onclick="confirm(...)"), écris un test qui les gère automatiquement.
  3. Documente en commentaire, pour chaque cas, quel événement Playwright tu écoutes et pourquoi.

Approfondissement

  • Piège fréquent : oublier Promise.all() autour de l'écoute d'événement et de l'action qui le déclenche. Si on les exécute l'un après l'autre au lieu de simultanément, on risque de rater l'événement (race condition classique).
  • Un iframe imbriqué dans un autre iframe nécessite de chaîner les frameLocator() — rare mais à savoir identifier si ça se présente.
  • Sans gestionnaire page.on("dialog", ...), Playwright rejette automatiquement les dialogues natifs par défaut : un test peut donc échouer silencieusement de façon inattendue si ce point est ignoré.

Validation

  1. Pourquoi utilise-t-on Promise.all() pour capturer un nouvel onglet plutôt que d'attendre après avoir cliqué ?
  2. Comment accède-t-on à un élément situé à l'intérieur d'un iframe ?
  3. Que se passe-t-il par défaut avec un dialogue natif si aucun gestionnaire page.on("dialog") n'est défini ?

Synthèse

  • Nouvel onglet, popup et téléchargement se capturent tous via un événement écouté en parallèle de l'action qui le déclenche.
  • frameLocator() donne accès au contenu d'un iframe comme s'il s'agissait d'une page normale.
  • Les dialogues natifs doivent être explicitement gérés via page.on("dialog", ...).

Module 1.5 — Debug et rapports

Trace Viewer, mode UI, screenshots/vidéos, lecture du rapport HTML.

Objectif

Diagnostiquer efficacement un test qui échoue, en utilisant les outils de debug intégrés à Playwright plutôt qu'en devinant ou en ajoutant des console.log au hasard.

Explication

Mode UI (npx playwright test --ui) : une interface graphique qui liste les tests, permet de les exécuter individuellement, et affiche un timeline pas-à-pas de chaque action avec l'état du DOM à chaque étape. C'est l'outil à privilégier en développement de test au quotidien.

Mode debug (npx playwright test --debug) : ouvre l'Inspector Playwright, qui met le test en pause avant chaque action et permet d'avancer manuellement, d'inspecter les locators en direct, et de voir pourquoi une action attend (ex. élément non visible).

Trace Viewer. Une trace est un enregistrement complet de l'exécution d'un test : captures d'écran à chaque étape, DOM snapshot, requêtes réseau, logs console. Configurée dans playwright.config.ts (typiquement trace: "on-first-retry" en CI pour ne pas alourdir chaque run), elle se rouvre après coup avec npx playwright show-trace trace.zip — l'outil de diagnostic le plus puissant pour comprendre un échec survenu en CI, là où on ne peut pas observer l'exécution en direct.

Screenshots et vidéos à l'échec. Configurables via screenshot: "only-on-failure" et video: "retain-on-failure" : capturent automatiquement l'état visuel au moment de l'échec, sans effort supplémentaire dans le code du test.

Démonstration

// playwright.config.ts (extrait)
import { defineConfig } from "@playwright/test";

export default defineConfig({
  use: {
    trace: "on-first-retry",
    screenshot: "only-on-failure",
    video: "retain-on-failure",
  },
});
# Mode UI — exploration interactive et pas-à-pas
npx playwright test --ui

# Mode debug — pause avant chaque action, Inspector ouvert
npx playwright test --debug tests/checkout.spec.ts

# Rejouer une trace enregistrée (ex. récupérée depuis la CI)
npx playwright show-trace test-results/checkout-retry1/trace.zip

Mise en pratique

À partir d'un test volontairement cassé (locator incorrect ou assertion erronée sur un scénario que tu as déjà écrit) :

  1. Configure trace: "on" temporairement et exécute le test qui échoue.
  2. Ouvre la trace générée et identifie précisément à quelle étape et pourquoi le test échoue.
  3. Relance le même test en mode --debug et observe la différence d'usage entre les deux outils.
  4. Corrige le test, puis repasse la config trace en "on-first-retry" (réglage recommandé pour ne pas alourdir l'exécution normale).

Approfondissement

  • Piège fréquent : laisser trace: "on" en permanence — cela ralentit sensiblement l'exécution et alourdit le stockage. Réservé au debug ponctuel ou au premier retry en CI.
  • En entreprise, la trace récupérée depuis les artefacts CI est souvent le seul moyen de diagnostiquer un échec qui ne se reproduit pas en local — un réflexe indispensable à acquérir dès maintenant plutôt qu'en urgence plus tard.
  • Un test qui échoue en local avec un message d'assertion clair ("expected 'Connecté' received 'Erreur de connexion'") n'a souvent pas besoin de la trace : elle est surtout précieuse quand la cause n'est pas évidente à la lecture du message d'erreur.

Validation

  1. Quelle est la différence d'usage entre le mode UI et le mode debug ?
  2. Que contient une trace Playwright, et pourquoi est-elle particulièrement utile pour un échec survenu en CI ?
  3. Pourquoi ne configure-t-on généralement pas trace: "on" en permanence ?

Synthèse

  • Mode UI pour développer et explorer, mode debug pour investiguer pas-à-pas un test précis.
  • Trace Viewer = l'outil de diagnostic le plus complet, notamment pour les échecs en CI.
  • Screenshots/vidéos à l'échec se configurent une fois pour toutes, sans effort dans chaque test.
