Module 2.1 — Organisation d'un projet de tests

Structurer un dossier de tests comme un vrai projet logiciel, pas comme un empilement de scripts.

Objectif

Mettre en place une arborescence de projet claire (tests, pages, data, utils) et une configuration multi-environnements exploitable en local comme en CI.

Explication

Un projet Playwright qui grossit sans structure devient vite ingérable : locators dupliqués, données codées en dur, tests qui se marchent dessus. La structure standard qui émerge dans la plupart des projets d'entreprise sépare clairement les responsabilités :

tests/            → les fichiers .spec.ts, un par fonctionnalité ou parcours
pages/            → les classes de Page Object (module 2.2)
fixtures/         → fixtures personnalisées (module 2.3)
data/             → jeux de données, factories (module 2.4)
utils/            → fonctions utilitaires partagées (formatage, helpers génériques)
playwright.config.ts

Sur la configuration multi-environnements : plutôt que de coder en dur une URL, on utilise des variables d'environnement (process.env.BASE_URL) injectées différemment selon qu'on exécute en local, en recette ou en CI. Playwright permet aussi de définir plusieurs projects dans la config pour exécuter le même ensemble de tests avec des paramètres différents (ex. un projet "mobile" avec un viewport réduit).

Démonstration

// playwright.config.ts
import { defineConfig, devices } from "@playwright/test";

export default defineConfig({
  testDir: "./tests",
  use: {
    baseURL: process.env.BASE_URL ?? "http://localhost:3000",
    trace: "on-first-retry",
  },
  projects: [
    { name: "chromium", use: { ...devices["Desktop Chrome"] } },
    { name: "mobile-safari", use: { ...devices["iPhone 13"] } },
  ],
});
# Exécution avec une base URL différente selon l'environnement
BASE_URL=https://recette.monapp.com npx playwright test
BASE_URL=http://localhost:3000 npx playwright test

Mise en pratique

  1. Réorganise le projet créé en Phase 0/1 selon la structure ci-dessus (tests/, pages/, data/, utils/, même vides pour l'instant sauf tests/).
  2. Modifie playwright.config.ts pour lire la baseURL depuis une variable d'environnement, avec une valeur par défaut sensée.
  3. Ajoute un second project simulant un affichage mobile et vérifie qu'un test existant passe dans les deux configurations.

Approfondissement

  • Piège fréquent : coder l'URL de l'application en dur dans chaque test — le jour où l'environnement de test change (nouveau domaine de recette, environnement de démo), il faut modifier des dizaines de fichiers au lieu d'une seule variable.
  • Ne pas sur-architecturer trop tôt : sur un petit projet, un dossier utils/ vide n'a pas de valeur. Créer la structure au fur et à mesure du besoin réel reste préférable à un squelette figé dès le premier jour.
  • En entreprise, les variables sensibles (URLs internes, credentials) transitent via un fichier .env non commité, chargé avec une librairie comme dotenv — approfondi au module 2.4.

Validation

  1. Pourquoi sépare-t-on les Page Objects (pages/) des fichiers de test (tests/) ?
  2. À quoi sert de définir plusieurs projects dans playwright.config.ts ?
  3. Quel est l'intérêt de piloter la baseURL par variable d'environnement plutôt qu'en dur dans le code ?

Synthèse

  • Structure standard : tests/, pages/, fixtures/, data/, utils/.
  • Les variables d'environnement pilotent la configuration selon l'environnement d'exécution.
  • Les projects permettent d'exécuter la même suite de tests dans des contextes différents.

Module 2.2 — Page Object Model

Le pattern central de tout framework Playwright/TypeScript professionnel.

Objectif

Concevoir et implémenter des Page Objects en TypeScript, comprendre leurs avantages et leurs limites, et refactoriser un test existant pour l'utiliser.

Explication

Le Page Object Model consiste à encapsuler, pour chaque page (ou composant significatif) de l'application, ses locators et les actions qu'on peut y réaliser, dans une classe TypeScript dédiée. Le test lui-même ne manipule plus de locators bruts : il appelle des méthodes métier comme loginPage.login(email, password).

Avantages : si un élément change de structure HTML, une seule ligne à corriger (dans le Page Object) au lieu de dizaines de tests. Les tests deviennent aussi plus lisibles : ils décrivent un scénario métier plutôt qu'une suite de manipulations techniques.

Limites : un POM mal conçu peut devenir une couche d'abstraction lourde qui ralentit plus qu'elle n'aide, notamment si les méthodes deviennent trop génériques ou si on encapsule des assertions dans les Page Objects (à éviter en général : les assertions restent dans le test, les Page Objects exposent des données ou des actions, pas des vérifications).

Alternative à connaître : le pattern Screenplay, plus orienté "acteurs et tâches" que "pages", plus adapté aux très gros projets avec des parcours transverses à plusieurs pages. Le POM reste largement suffisant et le standard de facto pour la majorité des projets, y compris en entreprise.

Démonstration

// pages/LoginPage.ts
import { Page, Locator } from "@playwright/test";

export class LoginPage {
  private readonly page: Page;
  private readonly emailInput: Locator;
  private readonly passwordInput: Locator;
  private readonly submitButton: Locator;

  constructor(page: Page) {
    this.page = page;
    this.emailInput = page.getByLabel("Adresse email");
    this.passwordInput = page.getByLabel("Mot de passe");
    this.submitButton = page.getByRole("button", { name: "Se connecter" });
  }

  async goto(): Promise {
    await this.page.goto("/login");
  }

  async login(email: string, password: string): Promise {
    await this.emailInput.fill(email);
    await this.passwordInput.fill(password);
    await this.submitButton.click();
  }
}
// tests/login.spec.ts
import { test, expect } from "@playwright/test";
import { LoginPage } from "../pages/LoginPage";

test("connexion réussie avec des identifiants valides", async ({ page }) => {
  const loginPage = new LoginPage(page);

  await loginPage.goto();
  await loginPage.login("camille.durand@exemple.com", "MotDePasse123!");

  // L'assertion reste dans le test, pas dans le Page Object
  await expect(page.getByText("Bienvenue, Camille")).toBeVisible();
});

Mise en pratique

  1. Reprends un test écrit en Phase 1 (par exemple le formulaire d'inscription du module 1.2).
  2. Crée une classe Page Object correspondante avec locators privés et méthodes publiques orientées action métier (pas une méthode par champ, mais une méthode qui remplit tout le formulaire d'un coup si cela a du sens).
  3. Refactorise le test pour qu'il utilise uniquement le Page Object, sans locator brut restant dans le fichier de test.
  4. Vérifie que le test passe toujours après refactorisation.

Approfondissement

  • Piège fréquent : mettre des expect() à l'intérieur des méthodes de Page Object. Cela mélange deux responsabilités (agir sur la page / vérifier un résultat) et rend les tests moins lisibles — garder les assertions dans les fichiers de test.
  • Une classe de Page Object trop "chirurgicale" (une méthode par clic individuel) n'apporte pas grand-chose : viser des méthodes qui représentent une intention utilisateur complète (login(), ajouterAuPanier()) plutôt qu'un mapping 1:1 avec chaque élément HTML.
  • Pour des composants réutilisés sur plusieurs pages (un header, une barre de recherche), créer un Page Object de composant à part, injecté ou instancié dans les Page Objects de page qui l'utilisent — évite la duplication.

Validation

  1. Pourquoi les assertions ne doivent-elles pas se trouver dans les méthodes d'un Page Object ?
  2. Quel est l'avantage principal du POM quand la structure HTML de l'application change ?
  3. Dans quel cas envisagerait-on le pattern Screenplay plutôt que le POM classique ?

Synthèse

  • Un Page Object encapsule locators + actions ; les tests appellent des méthodes métier, pas des locators bruts.
  • Les assertions restent dans les tests, jamais dans les Page Objects.
  • Le POM est le standard de facto ; Screenplay est une alternative pour des cas très transverses.

Module 2.3 — Fixtures et hooks

Factoriser la préparation et le nettoyage des tests de façon réutilisable et typée.

Objectif

Distinguer les hooks classiques (beforeEach/afterEach) des fixtures personnalisées Playwright, et créer une fixture réutilisable typée pour un besoin récurrent (par exemple un utilisateur déjà authentifié).

Explication

Hooks classiques. test.beforeEach() et test.afterEach() exécutent du code avant/après chaque test d'un fichier ou d'un describe. Simples et suffisants pour une préparation locale à un fichier de tests.

Fixtures Playwright. Plus puissantes : une fixture est une valeur ou un objet préparé automatiquement et injecté dans les tests qui la déclarent en paramètre, avec gestion automatique de sa création et de son nettoyage. Playwright fournit des fixtures natives (page, context, browser), et on peut créer les siennes en étendant test via test.extend().

L'avantage des fixtures personnalisées sur de simples hooks : elles sont typées, réutilisables sur tout le projet (pas seulement un fichier), composables entre elles, et ne s'exécutent que si le test les demande réellement — un gain de performance sur de gros projets où tous les tests n'ont pas besoin des mêmes préparations.

Démonstration

// fixtures/auth.fixture.ts
import { test as base } from "@playwright/test";
import { LoginPage } from "../pages/LoginPage";

type AuthFixtures = {
  utilisateurConnecte: void;
};

export const test = base.extend<AuthFixtures>({
  utilisateurConnecte: async ({ page }, use) => {
    // Préparation (équivalent d'un beforeEach, mais réutilisable et typé)
    const loginPage = new LoginPage(page);
    await loginPage.goto();
    await loginPage.login("camille.durand@exemple.com", "MotDePasse123!");

    await use(); // le test s'exécute ici

    // Nettoyage éventuel après le test (équivalent d'un afterEach)
  },
});

export { expect } from "@playwright/test";
// tests/panier.spec.ts
import { test, expect } from "../fixtures/auth.fixture";

test("un utilisateur connecté peut ajouter un article au panier", async ({
  page,
  utilisateurConnecte, // déclenche automatiquement la connexion avant le test
}) => {
  await page.goto("/produits/123");
  await page.getByRole("button", { name: "Ajouter au panier" }).click();

  await expect(page.getByTestId("cart-count")).toHaveText("1");
});

Mise en pratique

  1. Crée une fixture utilisateurConnecte comme dans l'exemple, en l'adaptant à ton projet fil rouge.
  2. Écris deux tests différents qui utilisent cette fixture et vérifie qu'aucun des deux ne duplique la logique de connexion.
  3. Compare mentalement (ou par écrit) ce que tu aurais dû écrire avec un simple beforeEach à la place — identifie ce que tu perdrais en réutilisabilité entre plusieurs fichiers de test.

Approfondissement

  • Piège fréquent : créer une fixture pour absolument tout, y compris des préparations utilisées une seule fois — un beforeEach local suffit dans ce cas, la fixture personnalisée se justifie surtout par le partage entre plusieurs fichiers de tests.
  • Les fixtures peuvent dépendre d'autres fixtures (composition), ce qui permet de construire des scénarios de préparation complexes tout en gardant chaque fixture simple et testée isolément.
  • Le mot-clé use() à l'intérieur d'une fixture est le point de passage obligé : tout le code avant est la préparation, tout le code après (s'il y en a) est le nettoyage exécuté même si le test échoue.

Validation

  1. Quelle est la différence principale entre un beforeEach classique et une fixture personnalisée Playwright ?
  2. À quoi sert précisément l'appel à use() dans la définition d'une fixture ?
  3. Dans quel cas un simple hook reste-t-il préférable à une fixture personnalisée ?

Synthèse

  • Hooks (beforeEach/afterEach) pour une préparation locale à un fichier.
  • Fixtures personnalisées (test.extend()) pour une préparation typée, réutilisable et composable sur tout le projet.
  • use() sépare la phase de préparation de la phase de nettoyage d'une fixture.

Module 2.4 — Données de test et configuration

Jeux de données, secrets, et paramétrage de tests — sans jamais commiter de credentials.

Objectif

Externaliser les données de test (JSON, factories) et les secrets (variables d'environnement) hors du code des tests, et paramétrer un même test avec plusieurs jeux de données.

Explication

Données statiques vs générées. Pour des données stables et prévisibles (un compte de test toujours identique), un fichier JSON dans data/ suffit. Pour des données qui doivent être uniques à chaque exécution (éviter les conflits, par exemple créer un compte avec un email déjà pris), on utilise une librairie de génération comme @faker-js/faker, souvent via une fonction "factory" qui construit un objet de test avec des valeurs aléatoires mais cohérentes.

Paramétrer un test. Plutôt que dupliquer un test pour chaque jeu de données, on boucle sur un tableau de cas et on génère un test par entrée — chacun apparaît séparément dans le rapport, ce qui facilite le diagnostic si un seul cas échoue.

Secrets et configuration. Les credentials, tokens ou clés d'API ne doivent jamais apparaître en dur dans le code ni être commités. On les place dans un fichier .env (ajouté au .gitignore dès la Phase 0), chargé via dotenv, et on documente dans un .env.example (commité, lui) les variables attendues sans leurs valeurs réelles — pratique standard pour que l'équipe sache quoi configurer sans exposer de secret.

Démonstration

// data/utilisateurs.json
[
  { "email": "admin@exemple.com", "role": "admin" },
  { "email": "viewer@exemple.com", "role": "viewer" }
]
// tests/permissions.spec.ts
import { test, expect } from "@playwright/test";
import utilisateurs from "../data/utilisateurs.json";

for (const utilisateur of utilisateurs) {
  test(`accès au tableau de bord pour le rôle ${utilisateur.role}`, async ({ page }) => {
    await page.goto("/login");
    // ... connexion avec utilisateur.email
    // ... assertions spécifiques au rôle
  });
}
// .env (jamais commité)
BASE_URL=https://recette.monapp.com
API_TOKEN=abc123secret

// .env.example (commité, sert de documentation)
BASE_URL=
API_TOKEN=
// data/factories/utilisateur.factory.ts
import { faker } from "@faker-js/faker";

export function creerUtilisateurAleatoire() {
  return {
    email: faker.internet.email(),
    motDePasse: faker.internet.password({ length: 12 }),
    nom: faker.person.fullName(),
  };
}

Mise en pratique

  1. Crée un fichier data/utilisateurs.json avec au moins 3 profils différents pour ton projet fil rouge.
  2. Écris un test paramétré qui boucle sur ces profils et vérifie un comportement différent selon le rôle.
  3. Installe @faker-js/faker et écris une factory qui génère un utilisateur avec un email unique à chaque exécution — utile pour un test de création de compte qui ne doit jamais entrer en conflit.
  4. Mets en place un fichier .env et .env.example, vérifie que .env est bien ignoré par Git.

Approfondissement

  • Piège grave et fréquent : commiter un token ou mot de passe réel "juste pour tester rapidement" — même supprimé ensuite, il reste dans l'historique Git. Toujours passer par .env dès le premier usage d'un secret.
  • Des données générées aléatoirement (faker) sont idéales pour la création, mais rendent le debug moins prévisible — pour des scénarios de lecture/vérification d'un état connu, préférer des données statiques et stables.
  • En CI, les secrets sont injectés différemment (variables d'environnement du pipeline, vault) — approfondi en Phase 4 ; le principe reste le même : jamais en dur dans le code.

Validation

  1. Pourquoi ne suffit-il pas de supprimer un secret commité par erreur pour le sécuriser à nouveau ?
  2. Dans quel cas préfère-t-on des données statiques à des données générées aléatoirement ?
  3. À quoi sert un fichier .env.example commité alors que .env ne l'est pas ?

Synthèse

  • Données statiques (JSON) pour des cas stables, factories (faker) pour des données uniques à chaque run.
  • Boucler sur un tableau de données génère un test distinct par cas dans le rapport.
  • Secrets toujours via .env non commité, jamais en dur dans le code.

Module 2.5 — Authentification et storage state

Éviter de se reconnecter à chaque test, et gérer plusieurs rôles utilisateurs efficacement.

Objectif

Mettre en place une authentification une seule fois, réutilisée par tous les tests qui en ont besoin, avec une gestion propre de plusieurs rôles utilisateurs différents.

Explication

Se reconnecter via l'UI au début de chaque test (comme fait la fixture du module 2.3) fonctionne, mais ralentit l'ensemble de la suite si des dizaines de tests en ont besoin. Playwright propose un mécanisme dédié : storageState, qui sauvegarde l'état d'authentification (cookies, local storage) dans un fichier JSON après une connexion réussie, puis le réinjecte directement dans les tests suivants sans repasser par le formulaire de connexion.

La pratique standard consiste à créer un fichier de "setup" exécuté une seule fois avant la suite de tests (via un project dédié en dépendance dans playwright.config.ts), qui se connecte et sauvegarde le storageState. Les autres projets déclarent alors ce fichier comme état de départ.

Plusieurs rôles. Pour tester différents niveaux de permission (admin, utilisateur standard, invité), on répète ce principe avec un fichier de storage state distinct par rôle, et on choisit lequel charger selon le test ou le project concerné.

Démonstration

// tests/auth.setup.ts
import { test as setup } from "@playwright/test";
import { LoginPage } from "../pages/LoginPage";

const adminFile = "playwright/.auth/admin.json";

setup("authentification admin", async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.goto();
  await loginPage.login("admin@exemple.com", "MotDePasseAdmin123!");

  await page.context().storageState({ path: adminFile });
});
// playwright.config.ts (extrait)
export default defineConfig({
  projects: [
    { name: "setup", testMatch: /.*\.setup\.ts/ },
    {
      name: "chromium-admin",
      use: { storageState: "playwright/.auth/admin.json" },
      dependencies: ["setup"], // le setup s'exécute avant ce project
    },
  ],
});
// tests/dashboard-admin.spec.ts
import { test, expect } from "@playwright/test";

// Pas de connexion ici : le storageState est déjà chargé
test("un admin voit le panneau de gestion des utilisateurs", async ({ page }) => {
  await page.goto("/dashboard");
  await expect(page.getByRole("link", { name: "Gestion des utilisateurs" })).toBeVisible();
});

Mise en pratique

  1. Crée un fichier auth.setup.ts pour ton projet fil rouge qui se connecte et sauvegarde un storageState.
  2. Configure un project dédié qui dépend de ce setup et charge le storageState sauvegardé.
  3. Écris un test qui vérifie qu'il est bien connecté d'entrée de jeu, sans aucune étape de login dans le test lui-même.
  4. Si ton application distingue plusieurs rôles, répète l'opération pour un second rôle et écris un test qui vérifie qu'un droit d'accès diffère entre les deux.

Approfondissement

  • Piège fréquent : commiter les fichiers de storageState générés (playwright/.auth/*.json) — ils contiennent des cookies de session réels et doivent être ajoutés au .gitignore, tout comme .env.
  • Le storageState a une durée de vie liée à la session côté application : si les tokens expirent rapidement, le setup doit s'exécuter à une fréquence adaptée (à chaque run reste le plus sûr et le plus simple par défaut).
  • Cette approche ne convient pas à un scénario qui teste explicitement le processus de connexion lui-même (formulaire, erreurs de credentials) — ce cas continue logiquement à passer par l'UI, comme vu en Phase 1.

Validation

  1. Quel problème concret storageState résout-il par rapport à une reconnexion systématique via l'UI ?
  2. Pourquoi ne faut-il jamais commiter les fichiers de storageState générés ?
  3. Dans quel cas un test doit-il malgré tout continuer à passer par le formulaire de connexion plutôt que d'utiliser un storageState préexistant ?

Synthèse

  • storageState évite de repasser par l'UI de connexion à chaque test.
  • Un fichier de setup dédié, exécuté en dépendance d'un project, génère cet état une seule fois.
  • Plusieurs rôles = plusieurs fichiers de storageState, jamais commités.

Clôture de la Phase 2 — évaluation pratique intermédiaire

Évaluation pratique intermédiaire : à partir d'une spec fonctionnelle donnée, reconstruire une partie du framework fil rouge avec POM, fixtures personnalisées et storage state, sans reproduire les erreurs vues aux modules précédents (assertions dans les Page Objects, secrets en dur, reconnexion systématique par UI).

CritèreAttendu pour valider la phase
ArchitectureStructure de projet claire, aucun locator brut dans les fichiers de test
POMClasses typées, assertions absentes des Page Objects
FixturesAu moins une fixture personnalisée réutilisée sur plusieurs tests
AuthAuthentification via storageState, aucun secret commité
