Module 3.1 — Tests API avec Playwright

Tout ce que tu fais aujourd'hui à la souris dans Postman, écrit en code typé et rejouable automatiquement.

Objectif

Écrire des tests API avec Playwright : requêtes GET/POST/PUT/DELETE, gestion de l'authentification par token, assertions sur le corps et le statut des réponses.

Explication

Playwright propose APIRequestContext, un client HTTP intégré, accessible via request dans un test, ou créé indépendamment via request.newContext() quand on veut un contexte API totalement séparé du navigateur (fréquent pour préparer des données avant un test UI — vu au module 3.2).

Le principe reste celui que tu connais déjà avec Postman : on envoie une requête avec une méthode, une URL, éventuellement des headers et un body, et on inspecte la réponse. La différence est que chaque appel devient reproductible, versionné dans Git, et exécutable automatiquement — plus besoin de rejouer une collection manuellement.

Pour l'authentification par token, deux approches courantes : passer le header Authorization à chaque requête, ou configurer un extraHTTPHeaders une fois pour tout un contexte de requêtes qui en a besoin partout.

Démonstration

import { test, expect } from "@playwright/test";

test("créer un utilisateur via l'API", async ({ request }) => {
  const response = await request.post("/api/users", {
    data: {
      nom: "Camille Durand",
      email: "camille.durand@exemple.com",
    },
  });

  expect(response.status()).toBe(201);

  const body = await response.json();
  expect(body).toMatchObject({
    nom: "Camille Durand",
    email: "camille.durand@exemple.com",
  });
  expect(body.id).toBeDefined();
});

test("accès à une ressource protégée avec token", async ({ request }) => {
  const loginResponse = await request.post("/api/auth/login", {
    data: { email: "admin@exemple.com", password: "MotDePasseAdmin123!" },
  });
  const { token } = await loginResponse.json();

  const response = await request.get("/api/admin/utilisateurs", {
    headers: { Authorization: `Bearer ${token}` },
  });

  expect(response.ok()).toBeTruthy();
  const utilisateurs = await response.json();
  expect(Array.isArray(utilisateurs)).toBeTruthy();
});

Mise en pratique

  1. Reprends une collection Postman que tu utilises (ou une API publique de test comme reqres.in) et identifie 3 requêtes représentatives (création, lecture, suppression).
  2. Transpose chacune en test Playwright TypeScript avec des assertions sur le statut ET sur le contenu de la réponse.
  3. Si l'API nécessite une authentification, écris un test qui récupère d'abord un token puis l'utilise pour une requête protégée.

Approfondissement

  • Piège fréquent : vérifier uniquement le status code sans inspecter le corps de la réponse — un 200 OK peut masquer une réponse vide ou incorrecte si on ne vérifie pas aussi les données retournées.
  • toMatchObject() vérifie qu'un sous-ensemble de propriétés correspond, utile quand la réponse contient des champs dynamiques (id, timestamps) qu'on ne veut pas comparer strictement.
  • Contrairement à un test UI, un test API n'a pas d'auto-waiting sur des éléments visuels : la réponse HTTP est soit reçue soit non, ce qui rend ces tests généralement plus rapides et plus stables que les tests UI équivalents — bonne raison d'en écrire davantage quand c'est pertinent.

Validation

  1. Pourquoi ne suffit-il pas de vérifier le status code d'une réponse API pour valider un test ?
  2. Que permet toMatchObject() que ne permet pas une comparaison stricte de l'objet entier ?
  3. Pourquoi les tests API sont-ils en général plus rapides et plus stables que les tests UI équivalents ?

Synthèse

  • APIRequestContext (via request) permet d'écrire des tests API typés et reproductibles.
  • Toujours vérifier statut ET contenu de la réponse, pas l'un sans l'autre.
  • L'expérience Postman se transpose directement : mêmes concepts, code en plus.

Module 3.2 — Combinaison UI + API

Utiliser l'API pour préparer l'état avant un test UI : plus rapide, plus stable, plus ciblé.

Objectif

Préparer les données nécessaires à un test UI via l'API plutôt que via l'interface, et vérifier une action UI par un contrôle croisé côté API.

Explication

Un test UI qui doit, par exemple, tester la modification d'une commande existante n'a pas besoin de créer cette commande en cliquant à travers toute l'interface : c'est lent, et ça teste un parcours (la création) qui n'est pas l'objet du test. La pratique professionnelle standard consiste à créer les données de précondition via l'API (rapide, fiable), puis à ne tester en UI que ce qui doit réellement l'être.

Dans l'autre sens, une vérification croisée consiste à effectuer une action en UI (par exemple modifier un profil) puis à vérifier via un appel API direct que la donnée a bien été persistée côté serveur — une double garantie que l'action a eu l'effet attendu, pas seulement un effet visuel côté client.

Ce principe rejoint directement la notion de pyramide des tests (approfondie en Phase 4) : privilégier les couches les plus rapides et stables (API) pour tout ce qui n'est pas strictement le comportement visuel/interactif à valider.

Démonstration

import { test, expect } from "@playwright/test";

test("modifier le nom d'une commande existante", async ({ page, request }) => {
  // Préparation via API : rapide, ne teste pas la création elle-même
  const creationResponse = await request.post("/api/commandes", {
    data: { produit: "Clavier mécanique", quantite: 1 },
  });
  const { id: commandeId } = await creationResponse.json();

  // Le test UI se concentre uniquement sur ce qu'il doit valider : la modification
  await page.goto(`/commandes/${commandeId}`);
  await page.getByLabel("Note interne").fill("Livraison urgente");
  await page.getByRole("button", { name: "Enregistrer" }).click();

  await expect(page.getByText("Modifications enregistrées")).toBeVisible();

  // Vérification croisée : la donnée est bien persistée côté serveur
  const verifResponse = await request.get(`/api/commandes/${commandeId}`);
  const commande = await verifResponse.json();
  expect(commande.noteInterne).toBe("Livraison urgente");
});

Mise en pratique

  1. Identifie sur ton projet fil rouge un test UI dont la précondition (créer un compte, un produit, une commande) pourrait être préparée via API plutôt qu'en cliquant dans l'interface.
  2. Réécris ce test en préparant l'état via l'API et en ne testant en UI que l'action réellement concernée.
  3. Ajoute une vérification croisée côté API après l'action UI.
  4. Compare le temps d'exécution avant/après — le gain devrait être visible.

Approfondissement

  • Piège à éviter : systématiser cette approche au point de ne plus jamais tester un parcours de création en UI — le parcours de création reste un scénario métier légitime à tester en UI au moins une fois, l'objectif est d'éviter de le répéter comme précondition dans chaque autre test.
  • Cette approche suppose que l'API testée est fiable et déjà couverte par ses propres tests (module 3.1) — sinon on risque de masquer un bug de préparation derrière un test UI qui semble passer.
  • En entreprise, cette pratique est un des leviers les plus efficaces pour réduire un temps d'exécution de suite de tests qui devient problématique en CI.

Validation

  1. Pourquoi prépare-t-on souvent l'état d'un test UI via l'API plutôt qu'en cliquant dans l'interface ?
  2. Pourquoi le parcours de création reste-t-il malgré tout légitime à tester en UI au moins une fois ?
  3. Que permet une vérification croisée API après une action réalisée en UI ?

Synthèse

  • Préparer les préconditions via API accélère et fiabilise les tests UI.
  • Vérification croisée API = double garantie qu'une action UI a eu l'effet attendu côté serveur.
  • Le parcours testé reste toujours couvert en UI au moins une fois — cette approche évite la répétition, pas la couverture.

Module 3.3 — Exécution parallèle et performance

Faire tourner une suite de tests plus vite, sans sacrifier la fiabilité.

Objectif

Comprendre le modèle de parallélisation de Playwright (workers, isolation), configurer l'exécution parallèle à bon escient, et savoir quand des tests doivent être exécutés en série plutôt qu'en parallèle.

Explication

Playwright exécute par défaut les fichiers de test en parallèle, répartis sur plusieurs workers (des processus indépendants). Chaque test dans un même fichier s'exécute séquentiellement par défaut au sein de ce worker, sauf configuration contraire. Chaque test bénéficie d'un context de navigateur isolé (cookies, storage propres) : deux tests parallèles ne se marchent donc pas dessus au niveau du navigateur.

Le nombre de workers se configure via workers dans playwright.config.ts ou en ligne de commande — un compromis entre vitesse (plus de workers) et ressources machine disponibles (CPU, mémoire), particulièrement pertinent en CI où les ressources sont souvent limitées.

Dépendances entre tests. Par défaut, les tests doivent être indépendants les uns des autres pour supporter la parallélisation. Quand un ordre est réellement nécessaire (rare, et à éviter si possible), test.describe.serial() force l'exécution séquentielle d'un groupe de tests — mais chaque test dans ce mode dépend de l'état laissé par le précédent, ce qui fragilise la suite : si le premier échoue, les suivants sont marqués comme ignorés, pas testés indépendamment.

Démonstration

// playwright.config.ts (extrait)
export default defineConfig({
  workers: process.env.CI ? 2 : undefined, // undefined = auto, basé sur les cœurs CPU
  fullyParallel: true, // parallélise aussi les tests au sein d'un même fichier
});
# Forcer un nombre de workers en ligne de commande
npx playwright test --workers=4

# Exécuter en série (utile pour isoler un problème de parallélisation)
npx playwright test --workers=1
import { test } from "@playwright/test";

// À utiliser avec parcimonie : les tests dépendent les uns des autres
test.describe.serial("processus de commande en plusieurs étapes", () => {
  test("étape 1 : création du panier", async ({ page }) => {
    // ...
  });

  test("étape 2 : validation de la commande", async ({ page }) => {
    // dépend de l'état laissé par l'étape 1
  });
});

Mise en pratique

  1. Mesure le temps d'exécution total de ta suite de tests actuelle avec --workers=1 puis avec le nombre de workers par défaut.
  2. Identifie si des tests de ton projet dépendent d'un état partagé (données créées par un test et utilisées par un autre) — un signe qu'ils ne sont pas correctement isolés.
  3. Si c'est le cas, refactorise-les pour qu'ils soient indépendants (chacun crée ses propres données, idéalement via API comme vu au module 3.2) plutôt que de les forcer en serial.

Approfondissement

  • Piège fréquent : des tests qui passent en local (peu de workers, machine puissante) mais échouent en CI (plus de workers relatifs aux ressources, ou l'inverse) à cause d'une dépendance cachée à un ordre d'exécution ou à une donnée partagée non isolée.
  • test.describe.serial() doit rester une exception : chaque test dépendant du précédent complique le diagnostic (un échec en cascade) et va à l'encontre de l'esprit même de tests automatisés indépendants.
  • Sur une base de données de test partagée entre plusieurs workers parallèles, une isolation par utilisateur/tenant de test (chaque worker travaille sur son propre jeu de données) évite les conflits — un sujet d'architecture à anticiper tôt sur un vrai projet.

Validation

  1. Qu'est-ce qui garantit qu'un test parallèle ne "voit" pas les cookies ou le storage d'un autre test qui s'exécute en même temps ?
  2. Pourquoi test.describe.serial() doit-il rester une exception plutôt qu'une habitude ?
  3. Cite une cause fréquente de tests qui passent en local mais échouent en CI liée à la parallélisation.

Synthèse

  • Playwright parallélise par défaut via des workers, avec un contexte navigateur isolé par test.
  • Le nombre de workers est un compromis vitesse/ressources, à ajuster surtout en CI.
  • L'indépendance des tests est la règle ; describe.serial() reste l'exception, avec ses inconvénients de diagnostic.

Module 3.4 — Diagnostiquer et fiabiliser les flaky tests

La compétence qui distingue un SDET junior d'un SDET confirmé.

Objectif

Identifier méthodiquement la cause réelle d'un test instable (flaky), au lieu de masquer le symptôme par un retry ou une attente arbitraire, et appliquer la correction adaptée à la cause identifiée.

Explication

Un test flaky est un test qui passe et échoue de façon non déterministe, sans changement du code testé ni du test lui-même. C'est un des problèmes les plus coûteux en automatisation : il érode la confiance dans toute la suite de tests, au point que des échecs réels finissent par être ignorés par réflexe ("c'est encore un flaky").

Causes typiques, par ordre de fréquence :

  • Problèmes de timing non couverts par l'auto-waiting : une animation, un état intermédiaire non pris en compte par l'assertion.
  • Données partagées entre tests exécutés en parallèle (vu au module 3.3) : un test modifie une donnée qu'un autre test parallèle utilise au même moment.
  • Dépendance à l'environnement : un test qui suppose un état initial (base de données vide, compte inexistant) qui n'est plus vrai après plusieurs exécutions.
  • Race conditions réseau : une action déclenchée avant qu'une requête réseau nécessaire soit terminée, sans attente explicite adaptée.

Méthode de diagnostic. Ne jamais se contenter de relancer le test en espérant qu'il passe. La trace (module 1.5) est l'outil central : comparer une exécution qui a échoué et une qui a réussi, repérer précisément à quelle étape et dans quel état le comportement diverge. Reproduire localement en isolant le test (--workers=1, exécution répétée du même test seul) permet souvent de distinguer un problème de timing d'un problème d'isolation.

Démonstration

# Isoler un test suspecté flaky : l'exécuter seul, plusieurs fois de suite
npx playwright test tests/panier.spec.ts --workers=1 --repeat-each=10
// Exemple de correction : problème de timing non couvert par l'auto-waiting
// AVANT (flaky) : l'assertion vérifie un état qui peut être transitoire
await page.getByRole("button", { name: "Ajouter au panier" }).click();
await expect(page.getByTestId("cart-count")).toHaveText("1"); // parfois "0" encore visible brièvement

// APRÈS : attendre explicitement la fin de la requête réseau concernée,
// car ici l'auto-waiting sur le texte ne suffisait pas (le compteur clignotait à "0" puis "1")
const responsePromise = page.waitForResponse(resp => resp.url().includes("/api/panier"));
await page.getByRole("button", { name: "Ajouter au panier" }).click();
await responsePromise;
await expect(page.getByTestId("cart-count")).toHaveText("1");
// Exemple de correction : donnée partagée entre tests parallèles
// AVANT (flaky en parallèle) : tous les tests utilisent le même email fixe
const email = "test@exemple.com";

// APRÈS : chaque test génère sa propre donnée, isolée
import { faker } from "@faker-js/faker";
const email = faker.internet.email();

Mise en pratique

Un fichier de tests volontairement instable sera fourni (ou : reprends un de tes tests et introduis délibérément une des causes ci-dessus pour t'entraîner à la détecter) :

  1. Exécute le test suspect plusieurs fois avec --repeat-each pour confirmer et quantifier l'instabilité.
  2. Analyse les traces des exécutions échouées et identifie laquelle des quatre causes typiques est en jeu.
  3. Rédige un court diagnostic écrit (2-3 phrases) expliquant la cause précise, avant de corriger.
  4. Applique la correction adaptée à la cause identifiée — pas un correctif générique.
  5. Reconfirme la stabilité avec plusieurs exécutions répétées après correction.

Approfondissement

  • Anti-pattern courant et dangereux : configurer des retries élevés en CI pour "absorber" les flaky tests sans les corriger. Cela masque le symptôme, ralentit la CI, et laisse le vrai problème intact — les retries doivent rester un filet de sécurité ponctuel (typiquement 1-2 en CI), jamais une solution de fiabilisation.
  • Un test qui échoue une fois sur cent est presque aussi problématique qu'un test qui échoue une fois sur trois : sur une suite de centaines de tests exécutés plusieurs fois par jour, un taux d'échec même faible génère un bruit constant qui dilue l'attention portée aux vrais échecs.
  • Documenter les flaky tests corrigés (cause + solution) dans un historique d'équipe est une pratique professionnelle utile : les mêmes causes reviennent souvent sous des formes différentes.

Validation

  1. Cite les quatre causes typiques de flaky tests vues dans ce module.
  2. Pourquoi augmenter les retries en CI n'est-il pas une solution de fiabilisation ?
  3. Quelle est la première chose à faire face à un test suspecté flaky, avant même d'essayer de le corriger ?

Synthèse

  • Un flaky test a toujours une cause précise (timing, données partagées, environnement, race condition réseau) — jamais du "hasard".
  • La trace et l'exécution répétée isolée sont les outils de diagnostic de référence.
  • Les retries en CI sont un filet de sécurité ponctuel, jamais un substitut à la correction de la cause réelle.
