Module 0.1 — Environnement de travail

Node.js, npm, Git, VS Code : le socle sur lequel tout le reste repose.

Objectif

À la fin de ce module, tu as un poste de travail complet : Node.js et npm installés et compris, Git configuré avec un premier dépôt fonctionnel, VS Code équipé des bonnes extensions.

Explication

Node.js et npm. Playwright est un framework JavaScript/TypeScript : il s'exécute via Node.js, le moteur qui permet de faire tourner du JS en dehors du navigateur. npm (Node Package Manager) est l'outil qui télécharge et gère les librairies (les "packages") dont ton projet dépend — Playwright en est un. Installe la version LTS (Long Term Support) de Node, la plus stable pour un usage professionnel.

Concrètement, un projet Node contient un fichier package.json qui liste ses dépendances et ses scripts, et un dossier node_modules qui contient le code réellement téléchargé. Ce dossier ne se commite jamais dans Git : il se régénère avec npm install.

Git. Tu n'as pas besoin de maîtriser Git à ce stade, seulement le cycle de base : modifier un fichier, le mettre en zone de préparation (add), l'enregistrer dans l'historique (commit), et envoyer vers un dépôt distant (push). Les branches et les Pull Requests viendront en Phase 4 quand on parlera de CI/CD et de travail en équipe — inutile de tout charger maintenant.

VS Code. C'est l'éditeur standard de l'écosystème Playwright. Trois extensions suffisent pour démarrer : Playwright Test for VS Code (exécution et debug des tests depuis l'éditeur), ESLint (détection d'erreurs et de mauvaises pratiques), Prettier (formatage automatique et cohérent du code).

Démonstration

# Vérifier les installations
node -v
npm -v
git --version

# Initialiser un dépôt Git dans un nouveau dossier
mkdir playwright-training && cd playwright-training
git init
git config user.name "Ton Nom"
git config user.email "ton.email@exemple.com"

# Premier commit (même vide, pour valider le flux)
echo "# Playwright Training" > README.md
git add README.md
git commit -m "Initial commit"

Mise en pratique

  1. Installe Node.js LTS et vérifie la version avec node -v.
  2. Crée un dépôt Git local nommé playwright-training, avec un premier commit contenant un README.md.
  3. Crée un compte GitHub si tu n'en as pas, crée un dépôt distant vide, et pousse ton commit local dessus (git remote add origin ... puis git push).
  4. Installe les trois extensions VS Code mentionnées et ouvre ton dossier de projet dans l'éditeur.

Approfondissement

  • Piège fréquent : commiter node_modules par erreur. Toujours créer un fichier .gitignore dès le premier commit avec au minimum node_modules/ et .env dedans.
  • En entreprise, on utilise presque toujours un gestionnaire de versions Node (nvm) pour pouvoir changer de version de Node selon le projet — bon réflexe à prendre dès maintenant même si tu n'as qu'un seul projet.
  • Configure Prettier avec un fichier .prettierrc partagé dans le projet : la cohérence de style compte plus que les préférences individuelles en équipe.

Validation

  1. À quoi sert le dossier node_modules, et pourquoi ne le commite-t-on jamais ?
  2. Quelle est la différence entre git add et git commit ?
  3. Que se passe-t-il si tu exécutes npm install dans un dossier qui ne contient pas de package.json ?

Synthèse

  • Node.js exécute le JS/TS côté machine, npm gère les dépendances via package.json.
  • Cycle Git de base : add → commit → push.
  • VS Code + extensions Playwright/ESLint/Prettier = environnement de développement prêt.

Module 0.2 — JavaScript essentiel pour l'automatisation

Le strict nécessaire de JS pour comprendre n'importe quel test Playwright.

Objectif

Lire et écrire des fonctions, manipuler des tableaux et objets, et surtout comprendre le fonctionnement asynchrone (Promises, async/await) — le point le plus critique, car Playwright est intégralement asynchrone.

Explication

Variables. Utilise toujours const par défaut (valeur qui ne change pas de référence), et let seulement si la variable doit être réassignée. var est obsolète et à bannir.

Fonctions fléchées. La syntaxe moderne privilégiée : const addition = (a, b) => a + b;. Tu les rencontreras partout dans les tests Playwright, notamment dans les callbacks passés à test().

Tableaux et objets. Les méthodes map, filter, find transforment ou recherchent dans un tableau sans boucle explicite. Le "destructuring" permet d'extraire des valeurs directement : const { name, email } = user;.

Asynchrone — le point clé. En JavaScript, une opération longue (requête réseau, attente d'un élément à l'écran) ne bloque pas le programme : elle renvoie une Promise, un objet qui représente "un résultat qui arrivera plus tard". Historiquement on gérait ça avec des callbacks (imbrications illisibles), puis avec .then(), et aujourd'hui avec async/await qui permet d'écrire du code asynchrone avec une syntaxe qui ressemble à du code synchrone. Playwright utilise await devant quasiment chaque action (await page.click(...)) car cliquer, naviguer ou lire le DOM sont des opérations asynchrones.

Démonstration

// Fonction fléchée + destructuring
const users = [
  { name: "Alice", role: "admin" },
  { name: "Bob", role: "viewer" },
  { name: "Chloé", role: "admin" },
];

const admins = users.filter(u => u.role === "admin").map(u => u.name);
console.log(admins); // ["Alice", "Chloé"]

// Une fonction qui simule une opération asynchrone (comme un appel réseau)
function attendre(ms) {
  return new Promise(resolve => setTimeout(resolve, ms));
}

// Version async/await : lisible, séquentielle
async function scenario() {
  console.log("Début");
  await attendre(1000); // on attend 1 seconde sans bloquer le reste du programme
  console.log("1 seconde plus tard");
}

scenario();

Mise en pratique

Dans un script Node.js (exercice.js) :

  1. Crée un tableau d'objets produits (nom, prix, catégorie) d'au moins 5 éléments.
  2. Utilise filter pour ne garder que les produits d'une catégorie donnée.
  3. Utilise map pour obtenir la liste des noms uniquement.
  4. Écris une fonction async qui simule le chargement des produits (avec un setTimeout enveloppé dans une Promise) puis affiche le résultat une fois "chargé".

Cherche d'abord seul avant de demander une correction — c'est prévu dans la méthode.

Approfondissement

  • Piège très fréquent : oublier await devant un appel qui retourne une Promise. Le code continue alors sans attendre le résultat, ce qui dans Playwright provoque des tests instables (flaky) car une action est tentée avant que la précédente soit terminée.
  • Une fonction déclarée async retourne toujours une Promise, même si elle ne contient pas de await — bon réflexe à intégrer tôt.
  • En entreprise, un code plein de .then().then().then() imbriqués est presque toujours un signe qu'il faudrait migrer vers async/await.

Validation

  1. Pourquoi Playwright utilise-t-il await devant la quasi-totalité de ses actions ?
  2. Que retourne toujours une fonction déclarée async, même sans await à l'intérieur ?
  3. Écris de mémoire la différence de syntaxe entre une fonction classique et une fonction fléchée.

Synthèse

  • const par défaut, let si réassignation, jamais var.
  • map/filter/find pour manipuler des tableaux sans boucle explicite.
  • Une Promise représente un résultat futur ; async/await en est la syntaxe lisible — c'est le cœur de tout code Playwright.

Module 0.3 — TypeScript appliqué

Le typage et la programmation orientée objet, prérequis direct du Page Object Model (Phase 2).

Objectif

Typer des variables, fonctions et objets ; écrire une classe avec des méthodes et des propriétés privées ; comprendre les interfaces et les types union suffisamment pour lire n'importe quel exemple Playwright officiel.

Explication

Pourquoi TypeScript en automatisation. Le typage statique détecte des erreurs avant l'exécution (faute de frappe sur une propriété, mauvais type passé à une fonction), et l'autocomplétion de l'éditeur devient bien plus fiable — précieux quand un framework de tests grossit et est maintenu par plusieurs personnes.

Types de base et interfaces. On type les variables (let age: number), les paramètres et retours de fonction, et surtout la forme des objets via des interface : interface User { name: string; email: string; role?: "admin" | "viewer"; }. Le ? marque une propriété optionnelle, et "admin" | "viewer" est un type union : la valeur ne peut être que l'une de ces deux chaînes précises.

Classes. Une classe regroupe des données (propriétés) et des comportements (méthodes). C'est la structure que tu utiliseras pour chaque Page Object en Phase 2 : une classe LoginPage contiendra par exemple les locators de la page de connexion et une méthode login(email, password). Les modificateurs private/public/protected contrôlent qui peut accéder à quoi : une bonne pratique est de rendre private tout ce qui est un détail d'implémentation interne.

Génériques (aperçu). Un type générique s'adapte au type qu'on lui passe, par exemple Array<string> est un tableau de chaînes. Il n'est pas nécessaire de les maîtriser en profondeur maintenant ; l'objectif est de ne pas être bloqué en les croisant dans la documentation Playwright.

Démonstration

// Interface : la forme attendue d'un objet
interface Utilisateur {
  nom: string;
  email: string;
  role?: "admin" | "viewer"; // propriété optionnelle, type union
}

// Fonction typée
function creerUtilisateur(nom: string, email: string): Utilisateur {
  return { nom, email, role: "viewer" };
}

// Classe avec propriété privée et méthode publique
class CompteBancaire {
  private solde: number;

  constructor(soldeInitial: number) {
    this.solde = soldeInitial;
  }

  deposer(montant: number): void {
    this.solde += montant;
  }

  consulterSolde(): number {
    return this.solde;
  }
}

const compte = new CompteBancaire(100);
compte.deposer(50);
console.log(compte.consulterSolde()); // 150
// compte.solde // Erreur TypeScript : 'solde' est privé

Mise en pratique

  1. Écris une interface Produit (nom, prix, quantité en stock).
  2. Écris une classe Panier avec une propriété privée articles: Produit[], une méthode ajouter(produit: Produit), et une méthode total(): number qui calcule la somme des prix.
  3. Instancie un panier, ajoute 3 produits, affiche le total.
  4. Volontairement, essaie d'accéder directement à panier.articles depuis l'extérieur de la classe et observe l'erreur TypeScript — c'est le but pédagogique de private.

Approfondissement

  • Piège fréquent : typer avec any pour "faire taire" une erreur TypeScript. C'est exactement ce que le typage est censé éviter — à n'utiliser qu'en tout dernier recours, jamais par facilité.
  • En Page Object Model, la convention est quasi systématique : les locators sont des propriétés privées ou readonly, les actions utilisateur (comme login(), ajouterAuPanier()) sont les seules méthodes publiques exposées.
  • Active strict: true dans tsconfig.json dès le départ : c'est plus dur au début, mais ça évite de prendre de mauvaises habitudes qu'il faudra corriger plus tard sur un vrai projet d'entreprise.

Validation

  1. Quelle est la différence entre une interface et une class en TypeScript ?
  2. Pourquoi rend-on souvent les locators private dans une classe de Page Object ?
  3. Que signifie le ? après un nom de propriété dans une interface ?

Synthèse

  • Les interface décrivent la forme des données, les class combinent données et comportements.
  • private/public structurent ce qu'une classe expose — base directe du POM en Phase 2.
  • Éviter any : le typage strict est un allié, pas une contrainte à contourner.

Module 0.4 — Premier projet Playwright

De l'installation au premier test vert, avec une lecture guidée de chaque fichier généré.

Objectif

Installer Playwright, comprendre la structure de projet générée, exécuter un test fourni et lire son rapport HTML. On ne cherche pas encore à écrire de vrais scénarios — cela commence en Phase 1.

Explication

La commande d'installation officielle génère une structure standard : un dossier tests/ avec un exemple de test, un fichier playwright.config.ts qui centralise la configuration (navigateurs ciblés, dossier des tests, options de rapport), et un dossier tests-examples/ avec des scénarios de démonstration.

playwright.config.ts est le fichier le plus important à comprendre dès maintenant : il définit entre autres les "projects" (les navigateurs sur lesquels les tests s'exécutent — Chromium, Firefox, WebKit), la baseURL, et le reporter utilisé pour générer les rapports après exécution.

Un test Playwright minimal se compose d'un bloc test() contenant un titre et une fonction async qui reçoit un objet page — la page de navigateur sur laquelle on agit.

Démonstration

# Installation dans un projet existant
npm init playwright@latest

# Cela installe @playwright/test, télécharge les navigateurs,
# et propose de créer un exemple de workflow GitHub Actions (à ignorer pour l'instant)
// tests/exemple.spec.ts
import { test, expect } from "@playwright/test";

test("la page d'accueil de Playwright a le bon titre", async ({ page }) => {
  await page.goto("https://playwright.dev/");
  await expect(page).toHaveTitle(/Playwright/);
});
# Exécuter les tests
npx playwright test

# Ouvrir le rapport HTML généré après exécution
npx playwright show-report

Mise en pratique

  1. Installe Playwright dans ton dépôt playwright-training créé au module 0.1.
  2. Exécute le test d'exemple généré et vérifie qu'il passe.
  3. Ouvre playwright.config.ts et identifie : la baseURL (si définie), la liste des projects, et le reporter configuré.
  4. Ouvre le rapport HTML et repère : le statut du test, sa durée, et où se trouveraient les traces/screenshots en cas d'échec.
  5. Commite la structure générée dans Git (attention au .gitignore vu au module 0.1 : node_modules/, test-results/, playwright-report/).

Approfondissement

  • Piège fréquent : commiter playwright-report/ et test-results/ — ce sont des sorties générées à chaque exécution, elles n'ont rien à faire dans le dépôt Git.
  • Playwright installe par défaut trois navigateurs (Chromium, Firefox, WebKit) : en entreprise, on limite souvent l'exécution locale à un seul navigateur pour aller plus vite, et on réserve la matrice complète à la CI (vu en Phase 4).
  • La commande npx playwright test --ui ouvre un mode interactif très utile dès maintenant pour visualiser l'exécution pas à pas — on l'approfondira au module 1.5.

Validation

  1. À quoi sert le fichier playwright.config.ts ?
  2. Pourquoi ne commite-t-on pas playwright-report/ dans Git ?
  3. Quels éléments un rapport HTML Playwright affiche-t-il après une exécution ?

Synthèse

  • npm init playwright@latest génère une structure standard prête à l'emploi.
  • playwright.config.ts centralise la configuration (navigateurs, baseURL, reporter).
  • npx playwright test exécute, npx playwright show-report affiche le résultat.
